# CR-005 Production 部署事故复盘报告

**项目：** Margin Share Calculator  
**日期：** 2026-11-09  
**事件类型：** Deployment Process Failure / Repeated Execution Failure  
**涉及平台：** GitHub、ChatGPT Work、ChatGPT Sites  
**最终状态：** 用户已确认验收完成；最终 Production Version、Deployment ID 及发布时间待补充平台记录  
**报告依据：** 今日对话中的 Work 执行报告、GitHub 核查结果及最新 Skill 文件

## 1. Executive Summary

### 1.1 事件概述

CR-005 原本是一项已有应用的功能变更及 Production 更新任务。

但实际执行过程中，多次出现：

- 已知失败的 `git clone` 操作被重复执行。
- GitHub DNS 故障与 Sites Git 仓库 DNS 故障混为一谈。
- Work 未优先复用已更新的 Skill。
- CR-005 需求被错误扩大，导致原有 API 功能回归。
- GitHub 与 Sites 独立仓库的同步关系没有在部署前充分确认。
- Sites Source SHA 与发布包 Source SHA 不一致。
- 已完成的开发和测试被反复重新讨论。
- Work 多次输出 BLOCKED，而没有及时识别仍可执行的恢复操作。
- 用户需要反复提供指令，才能推动下一阶段。

最终，在重新允许受控 DNS 检查及必要网络授权后，部署流程得以继续，用户随后确认验收完成。

### 1.2 核心结论

**这是一次以执行流程失效为主、同时包含需求理解错误的事件。**

Skill 已包含多数必要规则，但规则没有可靠地转化为实际操作。

此外，Recovery Skill 对 DNS 失败的限制过于容易被绝对化执行，导致系统把避免重复失败误解为禁止检查环境是否恢复。

## 3. 技术问题分析

### 3.1 问题 A：重复 GitHub DNS 故障

**现象**

Work 再次执行 `git clone`，出现：

`Could not resolve host: github.com`

但项目已经具备可用的 GitHub Connector。

**预期行为**

优先使用已连接的 GitHub Connector 读取和修改源码。

只有需要本地执行环境且无法通过现有工具完成时，才选择其他源码获取方法。

**实际偏差**

Work 没有先加载最新 Recovery Skill，就使用了此前已经失败的网络路径。

**原因判断**

主要属于执行规则未落实，而不是 Skill 缺少相关规定。

Recovery Skill §0.1 已明确要求：

- 执行前读取最新 Skill。
- 优先检查 GitHub Connector。
- 对没有环境变化的重复 DNS 失败进行熔断。

因此，这次重复 `git clone` 属于可避免的执行失误。

### 3.2 问题 B：DNS 熔断机制被过度执行

**现象**

Work 后续遇到 Sites 绑定仓库 DNS 问题：

`Could not resolve host: git.chatgpt-team.site`

在用户要求不要重复 DNS 失败后，Work 一度不再重新检查该连接状态。

**关键区别**

`github.com` 与 `git.chatgpt-team.site` 是两个不同的访问目标。

GitHub Connector 可以解决 GitHub 源码访问问题，但不能自动解决 Sites 绑定仓库的 Git 写入问题。

**真正的问题**

原本合理的规则：

> 没有条件变化时，不重复执行已经失败的操作。

被错误扩大成：

> 只要曾经发生 DNS 失败，就不要再次检查。

这种解释忽略了网络授权、执行环境和时间变化。

**根因分类**

- Skill 规则边界不够精确。
- Work 执行判断过度保守。
- 用户指令被脱离适用条件执行。

**正确恢复原则**

DNS 失败应记录目标域名、环境、时间、授权状态及错误。

只有在条件完全不变时才禁止重复尝试。

当授权或环境发生变化时，允许有限次数的受控重新验证。

### 3.3 问题 C：Sites Source SHA 不一致

**已确认记录**

| 项目 | SHA |
|---|---|
| GitHub 修复提交 | `9d876e2dc336ec71d0a82ab92b62209d09e6d5a0` |
| Sites 发布包来源 | `d7030e2498cb6dd20c184aaa9c9d1c7e78e38360` |
| Sites 当时绑定 HEAD | `c74580fa0ea2a173cbb610e81369d3b93a7fee7f` |

Work 确认 `d7030e2` 是 `c74580f` 的直接子提交。

因此，目标更新可以采用非破坏性的 Fast-forward。

**原因**

GitHub 和 ChatGPT Sites 使用不同的源码仓库。

GitHub 提交完成后，并不会自动证明 Sites 绑定仓库已经更新。

发布包基于较新的 Sites Source Commit，而绑定仓库 HEAD 仍停留在旧版本。

**根因**

源码同步步骤未完成。

**流程缺陷**

在构建和准备发布包之前，没有可靠确认：

1. Sites 绑定仓库当前 HEAD。
2. 是否具备源码写入权限。
3. 当前执行环境是否能够连接绑定仓库。
4. 发布包对应的 Source Commit 是否已经同步。

这项问题本应在部署预检阶段暴露。

### 3.4 问题 D：CR-005 需求理解错误

**原始业务目标**

首次打开页面保持空白，不自动恢复旧数据。

**错误实现**

将空白初始化扩大成行情必须通过 CSV/JSON 手动导入。

这导致原有 Yahoo Finance 行情获取功能受到影响。

**正确行为**

- 页面初始化为空白。
- 不自动获取行情。
- 用户可以主动调用 Yahoo Finance API。
- Payment Date API 保持独立。
- CSV/JSON 仍可作为其他数据来源。
- 回测使用当前会话中取得的数据。

**根因**

缺少对既有功能的兼容性检查。

这属于需求分析和回归测试覆盖问题，不属于 Sites 部署平台故障。

### 4.1 为什么 Skill 更新了，问题仍然发生？

主要有四个原因。

**原因一：Skill 不是强制执行引擎**

Skill 文件提供操作规范，但文件更新本身不会保证每一个 Work 会话都自动读取并遵守。

Recovery Skill §0.1 实际上已经明确说明：远程 Skill 更新不代表当前 Work 自动加载。

**原因二：没有验证 Skill 是否真正加载**

缺少可核实的执行前检查记录，例如：

- 本次读取了哪个 Skill 文件。
- 文件对应哪个 Git Commit。
- 哪些规则适用于当前任务。
- 哪些历史失败路径必须避开。

因此，无法单凭文件存在判断 Work 已经遵守。

**原因三：规则存在解释空间**

例如 DNS 熔断规则。

它明确禁止在没有新条件时重复失败操作，但没有足够突出：

- 不同域名应分别判断。
- 授权变化属于新的执行条件。
- 受控连通性检查不同于无限重试。
- 发现 DNS 问题不代表整个部署任务永久失败。

**原因四：执行流程过度依赖 Work 自行判断**

即使 Skill 已要求：

`GitHub → Sites Source → Save Version → Deploy`

实际操作仍可能跳过 Source Sync 的可用性验证。

因此，Skill 规定了流程，但没有形成足够可靠的执行检查点。

## 5. 根因与责任归类

| 问题 | 主要原因 | 是否可预防 |
|---|---|---|
| 重复 `git clone` | 未优先执行 Skill 和 Connector 路径 | 是 |
| 需求被错误扩大 | 需求理解及回归保护不足 | 是 |
| Sites SHA 不一致 | 源码同步步骤未完成 | 是，可提前发现 |
| DNS 解析失败 | Work 网络环境问题 | 不一定 |
| DNS 后直接停止 | 恢复策略执行过度保守 | 是 |
| 反复 BLOCKED | 未充分区分局部阻塞与整个任务失败 | 是 |
| 用户多次重复指令 | 自动恢复及断点续跑执行不足 | 是 |

### 5.1 责任判断

**AI 执行层面：主要责任。**

没有稳定加载和落实既有 Skill，导致重复诊断、重复交接及错误恢复判断。

**Skill 设计层面：次要但重要。**

规则已经覆盖主要场景，但部分内容不够明确，尤其是 DNS 熔断的解除条件和不同仓库的故障隔离。

**平台环境层面：技术阻塞因素。**

DNS 解析失败是实际发生的网络问题，但现有证据不足以确定其底层原因是 DNS 服务、网络出口、代理、沙箱限制还是授权状态。

**用户层面：无证据显示需要承担技术执行责任。**

用户已提供目标、授权及必要的方向纠正。网络授权仍属于需要用户批准的正常边界。

## 6. 为什么之前 V1、V2、V3 可以部署？

这次不能简单认为以前成功，所以现在一定应该自动成功。

历史版本成功只能证明：在当时的执行条件下，存在可用的发布路径。

它不能证明：

- 当前 Work 环境具有相同网络权限。
- 当前 DNS 状态相同。
- 当前绑定仓库连接仍可用。
- 当前会话已经加载相同 Skill。
- 当前发布包已同步到绑定仓库。

**真正需要复用的是经过验证的发布操作链，而不只是历史成功结果。**

当前 Recovery Skill 已要求历史成功优先，但历史操作记录尚未完整恢复。

这是长期可靠性方面仍需解决的问题。

## 7. 改善措施

### P0 — 必须改善

**A. 强制 Skill 加载确认**

每个 Work 任务开始前：

- 读取最新适用 Skill。
- 确认文件版本。
- 识别当前任务适用的执行规则。
- 若未成功读取，不得声称已遵守。

**B. DNS 故障按目标隔离**

分别记录：

- `github.com`
- `git.chatgpt-team.site`

不得把一个域名的故障直接推广到另一个域名。

**C. DNS 熔断必须有解除条件**

只有执行环境、网络权限或其他相关条件未变化时，才阻止重复尝试。

条件变化后，允许一次受控验证。

**D. Sites 发布前确认完整链路**

必须验证：

`GitHub → Sites Source Write → Sites HEAD → Build → Save Version → Deploy`

不能只确认 GitHub 可写，就认为 Sites 可以部署。

### P1 — 建议改善

**E. 建立统一 Deployment Checkpoint**

记录：

- GitHub Commit SHA
- Sites Source SHA
- Sites 当前 HEAD
- 测试结果
- 发布包 SHA-256
- 当前 Production Version
- 最后成功阶段
- 当前失败原因
- 可恢复的下一步

**F. BLOCKED 必须附带恢复条件**

例如：

`BLOCKED: DNS resolution failed for git.chatgpt-team.site`

同时记录：

`Resume when network authorization or execution environment changes.`

不能简单地把一次失败当成永久阻塞。

**G. 加强回归保护**

CR-005 这类初始化变更必须检查既有 API、计算、图表及数据导入功能。

避免为了实现新需求而删除已有能力。

### P2 — 长期改善

**H. 保留成功部署的实际执行记录**

每次部署成功后，保存：

- 实际源码同步方法。
- 构建命令。
- Source HEAD。
- Save Version 操作结果。
- Deployment ID。
- 线上验收结果。

以后应从成功记录直接恢复，而不是重新探索整套发布方法。

## 8. 不建议采取的措施

这次复盘不建议：

1. 继续无限增加 Skill 规则。
2. 为每次 DNS 失败建立一份新的 SOP。
3. 重写整个开发及部署流程。
4. 强制所有项目使用相同部署命令。
5. 为解决 Sites 同步问题而重新开发应用。
6. 把 GitHub Commit 成功当作 Production 成功。

**优先修正执行机制和现有规则的歧义，而不是继续扩大 Skill 文件。**

## 9. 最终结论

本次事件暴露了三个不同层面的问题：

**第一层：产品需求执行问题**

CR-005 的空白初始化被错误扩大，导致已有 API 功能回归。

**第二层：部署架构问题**

GitHub 与 ChatGPT Sites 使用不同源码仓库，但 Source Sync 没有得到可靠的前置验证。

**第三层：AI 工作流程问题**

即使 Skill 已更新，Work 仍可能未加载、未遵守或错误解释其中的规则。

其中第三层是本次最值得改善的地方。

### 最重要的经验

**Skill 更新 ≠ Skill 已加载 ≠ Skill 被正确执行。**

未来需要同时确认：

1. 规则已加载。
2. 执行路径符合规则。
3. 遇到故障时根据真实条件恢复。
4. 最终结果经过实际验证。

本次用户已确认验收完成，但最终发布版本、Deployment ID 和线上验收明细仍应补入记录，以形成完整的可复用部署证据。

**复盘建议：保留现有 Skill 架构，只针对本次确认的执行缺口进行最小修正。不要再通过不断叠加新规则来解决规则未执行的问题。**
