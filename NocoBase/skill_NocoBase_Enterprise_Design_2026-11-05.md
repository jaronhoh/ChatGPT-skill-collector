# NocoBase 3 — Enterprise Application Design & Delivery

> 核心原则：**人决定业务规则与验收；Agent 按项目规范实现；Core 承担通用能力；真实证据决定交付。** 本 Skill 是设计和协作规范，不替代当前应用随版本提供的 NocoBase 3 Skills、AGENTS.md 或官方 API 文档。

## 1. 何时使用与边界

- 适用于新建 NocoBase 3 应用、已有应用的功能增改、数据模型、流程审批、权限、测试、迁移和部署。
- 先识别项目版本、仓库、分支、应用根目录、现有数据库和运行环境；**已有应用必须在原应用继续，不另建一个**。
- 区分 NocoBase 3 Core（开源应用底座）与 Studio（多 Agent 团队治理，官方指南称专业版/企业版提供）。只使用 Core 即可开发和部署完整应用；**不强制购买 Studio**。
- NocoBase 3 当前文档注明 beta 接口可能变化；具体 CLI、API、包名、目录与命令必须以当前应用安装版本的 AGENTS.md、.agents/skills/ 和源码核实。不可把 NocoBase 2 技能用于 NocoBase 3。
- 与既有 PM Make → PRD Make → Chat First → GitHub → 按需部署工作流兼容。此 Skill 负责 NocoBase 实现约束，不覆盖用户已确认的业务需求、部署目标或既有项目规范。**NocoBase 服务端运行依赖须单独核实，不能假设 ChatGPT Sites 可承载其完整后端。**

## 2. 一句话精髓：Core First，业务代码最小化

在编码前先制作「需求 → Core 现成能力 → 需要自定义的差异 → 验证方式」映射：

| 业务问题 | 优先评估的 Core 能力 | 自定义代码只负责 |
|---|---|---|
| 业务实体、记录、文件 | 数据建模、数据库、文件 | 业务字段、约束、特定关系 |
| 员工、角色、数据范围 | 用户、认证、权限 | 业务操作和角色/记录范围规则 |
| 审批、状态、流转 | 工作流 / lifecycle / 审批能力 | 业务状态、转移条件、审批策略 |
| 消息与提醒 | 通知能力 | 触发时机、收件人和模板 |
| 页面、列表、表单 | 已安装的页面与组件能力 | 业务交互和必要 UI |
| AI/Agent | 已安装的 Agent 能力（如适用） | 特定业务工具与授权边界 |

**先检查已安装能力和许可证，再决定实现方式。** 不自行重复造权限、审批、通知、工作流引擎。Core 能力的具体 API 及可用插件以当前应用为准，不假定所有功能都已启用。

## 3. 设计先于代码（Design Before Code）

不要收到一句「做一个管理系统」就直接编码。先按一组一组的问题向用户确认会改变产品行为的决策，提出建议但不替用户决定。冻结或更新 `docs/design.md`，至少包括：

1. **业务目标与范围**：谁用、解决什么、MVP 做什么/不做什么。
2. **角色与权限矩阵**：菜单、操作、记录范围、管理员例外。
3. **数据模型**：实体、关系、字段、唯一性、必填、生命周期、旧数据。
4. **业务流程与状态机**：触发、允许转移、审批人、拒绝/撤回、并发冲突。
5. **页面与交互**：列表、详情、筛选、输入校验、空值、错误状态、中英文（如需要）。
6. **交付计划与验收**：按功能拆分，每阶段可观察的完成条件。
7. **开放问题与风险**：阻塞决策、迁移影响、数据保护、集成依赖。

在应用 `AGENTS.md` 登记 `docs/design.md`：**改业务前先读；需求变更影响设计时先更新设计，再改代码。** 如果已有等效设计文件或用户已有 PM/PRD 文档，应引用和复用，不机械重复创建。

单项需求至少写明：**谁使用、要做什么、什么规则/数据不能动、怎样验收**。较大改动先输出影响范围、待确认决策、测试计划，确认后执行。

## 4. AGENTS.md 与版本化 Skills：跨 Agent 的共同契约

应用创建后先读取：
- `AGENTS.md`：短小的项目规则和索引。
- `.agents/rules/`：项目自有的业务与工程约定。
- `.agents/skills/`：依赖同步的、与已安装 NocoBase 版本匹配的开发技能，**不要直接手改自动同步内容**。
- `docs/design.md`：业务设计与分步验收。
- 应用实际 `package.json`、相关源码、测试、迁移及配置。

保持 `AGENTS.md` 精简，把详细规则放进项目规则文件；不复制整套官方 Skills。官方 v3 源码仓库要求根 AGENTS.md 不超过 32 KB、细节由规则索引维护；**这是上游仓库约定，可借鉴，但不要未经检查强制套用到所有用户应用**。

官方 v3 源码仓库的分支命名、changeset、PR 模板等规则属于**上游贡献流程**；用户应用遵循自身 GitHub 规范，不照搬上游特有 CI/发布政策。

## 5. 按纵向功能切片交付

每一阶段尽可能完成 **数据迁移 → API → 页面 → 角色/流程 → 测试 → 人工验收 → Git Commit**，而非先做全库、再做所有页面、最后才测。

- **数据**：关键字段唯一约束在数据库层落实，输入框旁提供清晰错误；可选唯一字段须明确空值语义。迁移前扫描历史冲突并报告，不擅自清洗。
- **迁移**：已执行或已合并的迁移不得原地改写；用新迁移修正。保留升级、回滚和已有数据的兼容性；实际规则以应用版本为准。
- **API**：每个操作独立授权，遵循项目 HTTP API 规范并出现在接口文档；不能只依赖页面隐藏按钮。
- **页面**：列表、搜索、筛选、创建、编辑、空值、异常与刷新持久化都要验收；避免无必要的自建组件。
- **审批**：定义状态机、角色职责、条件规则、通知、操作日志和并发保护；参数需管理员可调时使用适合的 Core 配置能力。
- **完成门槛**：测试、实际 UI 操作、旧数据回归及用户验收分别记录，未执行不得声称通过。

## 6. 权限是三层，不是一层

每个角色逐项检查：
1. **UI**：只能看到有权访问的菜单、数据和操作按钮。
2. **API**：即使手动构造请求也无法执行越权动作。
3. **数据范围**：例如「本人提交」「分配给我」与「全部」必须在服务端生效。

操作按钮应同时满足 **业务状态允许** 与 **当前角色授权**。覆盖查看、创建、编辑、审批、撤回、发放、管理配置等操作；用真实不同账号做正向和越权反向测试。默认角色/种子数据更新须保护用户后续手工修改，不得每次部署强制覆盖。

## 7. 工作流与审批：状态机 + 不变量

- 显式声明状态及允许转移，例如草稿 → 待审批/待发放 → 已发放，另含驳回/撤回；不是任意字段更新。
- 审批人不能审批自己的申请等业务规则必须服务端执行；按提交时规则或实时规则判断的时点须写入设计。
- 每步记录操作者与时间，处理过期页面、重复提交、并发审批、撤回与失败重试。
- 审批通过后的设备/库存/负责人变更必须有一致性和失败处理方案；通知只发送给应接收者。
- 可配置规则应使用合适的 Core 工作流参数或设置机制，避免硬编码；核实当前版本具体实现。

## 8. 验收 Agent 的工作：真实场景优先

按每个角色的日常流程手动跑一遍，并检查：
- 旧记录兼容：新可选字段对旧数据应正确显示空值，不能误变成 1970 年日期。
- 日期：日期与日期时间分开；检查时区、边界日期和空值。
- 约束：重复唯一值、必填、非法状态转移均被拒绝且错误可理解。
- 权限：UI 隐藏与 API 拒绝均成立；数据范围正确。
- 持久化：刷新、重启或重建容器后数据仍在（按环境与范围）。
- 测试：运行与变更相关的 lint、typecheck、单元/集成、迁移和必要回归测试，记录真实结果。

不合格就提供 **角色/数据/复现步骤/实际结果/期望结果/截图或日志**，让 Agent 修复并复测；不能仅凭「Agent 说完成」验收。大仓库只运行受影响包及消费者的必要测试，范围扩大须有理由。

## 9. 部署与运行：镜像、配置、数据分离

官方指南以 Docker + Linux 服务器为例；是否采用 Docker/PM2 由真实环境决定。发布前检查目标环境支持 NocoBase 服务端、数据库、文件存储、密钥、路由、备份和持久化。

- **镜像/构建产物**可重新生成，按版本标记。
- **配置与密钥**放环境安全存储/部署目录，不进 Git、不进镜像；不要向聊天输出密码。
- **数据库与上传文件**持久化并备份；重建容器不应丢失。
- **发布流程**：确认源 Commit → 构建 → 备份 → 配置检查/连接检查 → 部署 → 健康检查 → 登录与业务烟测 → 持久化复核。
- 生产部署和数据库迁移属高风险动作；有数据覆盖、删除、权限变化时先取得明确授权并具备回滚方案。
- 开发数据不会自动成为生产数据；不得未经批准复制用户/业务记录到生产。
- GitHub commit、CI 通过、部署成功、业务验收是不同状态，分别记录证据。

## 10. ChatGPT Chat First 的执行策略

1. 在 Chat 中完成 PM/PRD/设计、影响分析、代码审查、测试规划；有真实 GitHub 写入工具时可直接提交已确认文档。
2. 只有需要当前聊天无法执行的本地运行、数据库操作、浏览器端到端验证、服务器部署时，才交给具备能力的 Codex/Work；只交接最小剩余范围。
3. 若用户现有 NocoBase 版本或环境与官方指南不同，先核对当前项目的 AGENTS.md 和本地技能，不猜 CLI。
4. 如项目同时使用 ChatGPT Sites，必须先核实 Sites 的真实服务端运行能力；不可将 GitHub 同步等同于 NocoBase 后端部署。
5. 若用户只要求设计或 GitHub 文档更新，到达业务终点即停止，不自动部署。

## 11. 每次开发的标准输出

- **目标与范围**：业务结果、当前项目/版本、明确不做。
- **设计依据**：docs/design.md、AGENTS.md、相关 NocoBase Core 能力。
- **实现映射**：数据/迁移、API、页面、工作流、权限、通知及复用的插件。
- **变更与证据**：实际文件、Commit/PR、已运行测试、人工验收、未验证项。
- **数据与部署风险**：旧数据、迁移、备份、回滚、环境。
- **下一步**：一个最小可执行动作；无需发布时不自动扩展。

## 12. 快速质量门槛

- [ ] 角色、业务规则、数据模型、流程、页面、验收标准已确认。
- [ ] 已读取当前项目 AGENTS.md、设计文档和版本匹配的 Skills。
- [ ] 优先复用 Core，新增业务代码有明确必要性。
- [ ] 数据约束、迁移兼容、旧数据与失败路径已检查。
- [ ] UI、API、记录范围三层权限通过实际验证。
- [ ] 审批状态、并发、通知和审计符合设计。
- [ ] 真实测试与人工验收分别记录。
- [ ] 未经授权不迁移/覆盖生产数据，不擅自部署。
- [ ] GitHub、CI、部署、业务验收状态独立记录。
