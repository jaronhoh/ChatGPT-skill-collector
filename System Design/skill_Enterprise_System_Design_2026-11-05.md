# Enterprise System Design — 通用系统设计与交付规范

> 通用执行边界、按需加载与完成标准以仓库根目录 `AGENTS.md` 为准；不必为普通任务预先读取其他 Skill。

> **核心定位**：这不是 NocoBase 开发 Skill。NocoBase 只是提炼规范的参考案例。任何项目均以其真实技术栈、现有架构、官方文档和用户业务目标为准。不要因为本 Skill 的来源而引入 NocoBase、NocoBase CLI、插件或目录结构。

## 1. 适用范围与优先级

- 适用于新系统规划、现有系统扩展、功能开发、架构评审、数据设计、权限、审批、测试和部署。
- 以**用户明确需求 > 当前项目已有决策与设计 > 实际框架/平台规范 > 本通用 Skill 的默认建议**为优先级；安全、数据保护和必要授权不可被低优先级约定绕过。
- 开始时识别：业务目标、现有系统、技术栈、运行环境、代码仓库、数据源、集成依赖、使用者、交付终点。
- Chat-first 开发与 GitHub：需求 → PM/PRD（视规模）→ 设计 → 开发 → 真实测试 → GitHub → 按需部署 → 发布验证。**不是每次必须走完整条链**。

## 2. 设计先于代码，但按风险控制设计深度

复杂功能先明确：谁用、要解决什么、输入输出、关键数据、规则、状态、异常、权限和验收方式。普通局部修复可以采用简短变更说明，不强制编写大篇设计文档或等待额外审批。

建议维护单一权威设计文档（可为 `docs/design.md` 或项目已有 PRD/FDD）：

1. 目标、非目标、角色与使用场景。
2. 系统边界、上下游、第三方集成、数据流与失败恢复。
3. 业务实体、关系、字段、唯一性、生命周期、历史数据兼容。
4. 业务流程、状态机、审批/撤回/拒绝、并发和幂等性。
5. UI 页面、交互、响应式、可访问性、语言和错误反馈。
6. 认证、角色、操作权限、记录级/租户级数据隔离、审计。
7. 非功能要求：性能、可用性、可观测性、安全、备份和恢复。
8. 分阶段交付、测试策略、可观察验收标准、开放问题和风险。

只有影响业务行为的关键未决事项才需要用户决策；不得反复要求用户确认已经决定的事项。

## 3. Reuse Before Build：先复用再自建

为每项需求建立「业务能力 → 现有平台/库/服务 → 差异化开发 → 验证」映射。优先复用已安装且适用的身份认证、权限、数据访问、表单、工作流、通知、任务队列、日志和 UI 组件。

- 不重复开发通用引擎；但必须评估许可、可移植性、运维成本、扩展性与安全性。
- 优先沿用项目现有技术栈和 UI 设计系统；在适合 React 项目时优先评估 shadcn/ui，**不是强制所有框架使用它**。
- 选型要写清「为什么复用/为什么自建」及约束；不要因为参考 NocoBase 就假设目标平台具备相同能力。

## 4. Documentation as Contract：文档是协作契约

建立清晰的文档层次，而非依赖单次 AI 对话：
- **入口规则**：`AGENTS.md`、`CONTRIBUTING.md` 或项目约定的说明文件，保持简洁，指向真实来源。
- **业务设计**：PRD、FDD、`docs/design.md` 或现有等效文件，记录已确认规则和决策。
- **工程规范**：按主题组织的架构、数据库、API、UI、权限、测试、发布规范。
- **实现参考**：框架官方文档、版本匹配的开发 Skill、接口规范、示例和迁移手册。
- **状态记录**：实际测试、GitHub SHA、部署版本、验收结果和未解决风险。

**引用链追踪是强制方法**：阅读入口文件后，必须根据当前任务继续阅读其链接的其他 Markdown / 文档（包括二级及更深的任务相关引用），直到找到可执行约束。不能只读 `AGENTS.md` 的目录标题就声称理解完整规范。

仅追踪与任务有关的文档；不要每次通读全仓库。读取失败、版本不一致、链接不存在时明确记录未验证。**不得把参考项目的专属命令、目录、接口和上游贡献流程自动移植到其他系统**。

## 5. Vertical Slice Delivery：按可验收业务功能切片

按业务价值拆分，每个切片尽可能贯穿：数据 → 服务/API → UI → 权限/工作流 → 测试 → 用户验收 → Commit。

- 先实现最小可用的端到端流程，再逐步扩展异常、角色和集成。
- 每次改动记录影响范围与回归风险；不把代码生成或静态审查称为已测试。
- 现有系统先读取真实代码和配置，保留现有 URL、数据、权限、集成和部署入口。
- 选择正确的模块归属，避免把所有逻辑塞进控制器、组件或单个服务。

## 6. 数据建模与安全演进

- 明确实体、主键、关系、唯一性、必填、索引、数据归属、删除/归档策略和数据保留。
- 业务约束不能仅依赖前端校验；必要约束应在数据库/服务端保证。
- 迁移应确定性、可审查、可测试；**已经执行或合并的迁移不原地改写，优先新迁移修正**（具体以所用迁移框架约定为准）。
- 处理旧数据、空值、时区、重复记录、历史状态和并发更新；明确可回滚/不可逆变更。
- 不在未经授权时重置、清理、覆盖或复制生产数据；区分只读数据快照与可恢复备份。

## 7. 业务状态机、审批与自动化

- 明确状态、合法转移、触发条件、审批职责、拒绝/撤回/重试、操作日志与通知。
- 状态转移、审批人资格和数据权限必须由可信服务端执行。
- 处理重复提交、并发审批、过期页面、幂等性、事务边界与失败补偿。
- 将经常变化的业务规则配置化，但不为简单场景过度设计规则引擎。

## 8. Security by Design：三层授权

| 层次 | 验证重点 |
|---|---|
| UI | 仅显示允许的菜单、按钮、数据及交互 |
| API / 服务端 | 手工构造请求也无法越权；鉴权先于敏感读取和写入 |
| 数据范围 | 本人/部门/租户/全部的行级范围由服务端约束 |

覆盖正向与反向测试、跨角色、跨租户、敏感字段、管理员操作和审计。**隐藏按钮不等于安全**。认证、授权、输入验证、日志脱敏和密钥管理分别设计。

## 9. UI 与体验设计

- 以用户任务流设计页面，不只按数据库表生成 CRUD。
- 检查列表、详情、创建/编辑、搜索/筛选、空值、加载、错误、权限不足、移动端适配及必要的多语言。
- 继承既有设计系统；新视觉决策须与宿主一致。
- 按变更规模选择 Quick（局部修复）、Theme（主题）、Full（复杂跨模块）流程；复杂流程先设计，简单变更不制造不必要审批。

## 10. Evidence-Based Acceptance：以真实证据验收

- 测试矩阵包含：正常路径、异常路径、边界值、权限越权、旧数据、并发、失败恢复、持久化和必要回归。
- 记录哪些检查**实际执行**、在哪个环境执行、输入、预期、实际结果和证据；未运行标记 Not tested。
- 按影响范围运行 lint、typecheck、单元、集成、端到端和浏览器验证；不要求无关全仓库测试。
- AI 报告「完成」不是验收；用户确认功能可用也不自动证明生产发布或源码映射正确。
- 每个问题给出复现步骤、角色、数据、预期/实际结果、日志和修复后的复测结果。

## 11. Controlled Release：安全交付与运维

- 区分：需求验收、GitHub 代码/PR、精确 Head 的 CI、目标平台部署、运行源码映射；独立记录证据。
- 根据实际平台选择部署方式；先核实运行环境是否支持前端、服务端、数据库、定时任务和持久化。**不得假设不同托管平台具有相同能力。**
- 生产数据变更需明确授权、备份/回滚方案、密钥隔离、配置检查和上线烟测。
- 已有系统优先更新原系统，保留 URL、数据、配置与权限；Commit/Merge 不等于部署。
- 用户确认现有系统已满足需求且未要求额外发布时，允许停止发布工作并如实记录 `User confirmed — no deploy needed`。

## 12. 每次开发的标准交付摘要

1. **业务目标与本次终点**：已确认需求、范围、非目标。
2. **依据**：实际读取的项目文件、引用链、框架官方文档及版本。
3. **设计与实现**：数据、API、UI、权限、流程、复用能力、受影响文件。
4. **验证**：实际运行的测试、结果、GitHub Commit/PR、用户验收、未验证事项。
5. **风险与下一步**：数据迁移、回滚、部署影响及一个最小可执行动作。
