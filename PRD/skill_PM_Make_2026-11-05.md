# PM Make

## 默认开发执行策略：ChatGPT Chat First（2026-10-24 更新）

> **用户已确认的新规则：开发与测试优先在 ChatGPT 普通聊天中完成；只有确实需要时才使用 ChatGPT Work；通过验证后才部署到 ChatGPT Sites。** 此规则适用于新项目和既有项目，并覆盖本 Skill 中任何“默认先交给 Work 开发”的旧建议；不覆盖用户针对单次任务的明确指令。

1. **规划与设计优先 Chat**：需求澄清、PM/PRD、架构讨论、UI 设计、代码方案和审查优先在普通聊天完成。Web UI 默认优先评估 [shadcn/ui](https://ui.shadcn.com/) 和兼容的 Tailwind CSS；不适用时解释原因。
2. **开发优先 Chat**：先使用当前聊天实际可用的工具、连接器及代码能力推进实现、修复与迭代。能在 Chat 完成的，不因任务属于“开发”就主动转交 Work；但不得假设 Chat 一定具备本地仓库写入、终端或运行时能力。
3. **测试优先 Chat**：先在聊天环境中进行可实际执行的验证、代码审查和回归检查。区分 `实际执行并通过`、`执行失败`、`仅静态审查`、`测试方案未执行`；不得将生成代码或建议测试命令称为已测试通过。
4. **仅在必要时使用 Work**：当需要的本地文件/仓库编辑、浏览器交互、运行命令、端到端测试或部署无法由当前聊天工具完成时，才将**最小必要范围**交给 Work 或其他具备权限的执行端。Work 只处理尚未完成的步骤，不重复已验证工作；遵守当前平台的工具路由限制。
5. **GitHub 源码管理**：优先用 GitHub 保存与核对代码、PRD、Commit、PR、测试证据；提交或合并不等于已发布。未真正写入或验证时标记未完成。
6. **Sites 最后部署**：开发完成且必要测试有真实通过证据后，才进入 ChatGPT Sites 部署。先验证 Sites 技术兼容性；更新既有项目时保留原 Site、URL、数据、权限和配置，必要时准备回滚与取得授权；部署后实际验证运行状态。
7. **阻塞处理**：若聊天无法执行必要测试或缺乏真实环境，明确列出缺口；不可因“Chat 优先”而跳过测试或假称具备执行能力。必要时按上述最小范围升级到 Work，再部署。

**默认顺序：** PM Make → PRD Make → shadcn/ui（适用时）→ Chat 开发 → Chat 测试与审查 → GitHub 同步与核验 → Sites 部署 → 上线验证。Work 不是默认阶段，而是按需的执行补充。


## 默认 Web UI 与发布平台（2026-10-21 新增）

> 本节适用于**新开发的 Web 项目**；如果用户明确指定其他 UI 技术、平台，或既有项目已有经确认的技术决策，以用户明确要求和项目既定约束为准。不要把“默认优先”理解成无条件强制。

- **UI 首选**：优先评估并使用 [shadcn/ui](https://ui.shadcn.com/) 的适用组件，配合与项目兼容的 Tailwind CSS；优先复用组件而非重复造轮子，保持一致的视觉规范、响应式布局、键盘操作和无障碍体验。
- **适用性检查**：确认前端框架、组件依赖、构建方式、许可、维护成本及既有设计系统是否兼容。若不适合，说明原因、影响与替代方案，不未经确认更换既有项目 UI 技术栈。
- **默认发布目标**：新 Web 项目优先规划发布到 **ChatGPT Sites**；开发前实际核实目标 Sites 环境对框架、构建产物、路由、API、数据库、鉴权、环境变量、密钥、持久化及自定义域名等能力的支持。未经验证不得承诺某项 Sites 能力可用。
- **源码管理**：优先将 GitHub 作为源码与版本追踪来源；项目若有已确认的其他仓库策略，遵循既有约定。
- **部署边界**：规划、提交、合并、测试、Sites 部署、上线验证是不同阶段；只有真实执行且有证据时才标记完成。需要发布权限或操作工具时，应说明实际能力边界，不能将生成部署指令等同于已部署。
- **更新现有 Site**：默认沿用现有 Site 与 URL，保护生产数据、权限、配置、Secrets 和既有功能；破坏性更改、数据清空或高风险生产发布需明确授权及回滚方案。
- **项目记录**：在产品定型稿、PRD、技术方案或交接指令中，分别注明 UI 选择、Sites 可行性检查结果、尚未验证的限制及实际发布状态。

**本 Skill 的具体应用：**PM Make 应在产品定型阶段记录默认 UI、发布平台及兼容性待验证项；不得在业务需求尚未确认时把技术偏好当作业务需求。

## 1. 目标

PM Make 用于把粗略产品想法收敛成冻结版产品定型稿（Product Shipping Brief）。通常控制在约 1000 个中文字或一页以内，可直接用于 AI Coding、原型生成，或作为 PRD Make 的输入。

本 Skill 不是一次性提示词。必须采用工作区式流程：初始化 6 个聚焦文件，逐个文件填充，暴露开放问题；只有在用户确认没有未解决产品决策后，才能冻结最终定型稿。

## 2. 项目工作区

不要创建 `skills/` 或 `templates/` 文件夹作为产品项目内容。

当用户开始一个新产品时，优先在用户指定的 GitHub / Google Drive 产品工作区中创建：

```text
<ProductName>/
└── 01-产品定义/
    ├── 01-基本描述.md
    ├── 02-JTBD场景.md
    ├── 03-范围边界.md
    ├── 04-页面流程.md
    ├── 05-开放问题.md
    └── 06-最终定型稿.md
```

如果产品工作区已经存在，复用现有文件，不重复创建。

如果 GitHub 和 Google Drive 均已连接：
- 优先保持两边相同的产品目录和文件命名。
- GitHub 可作为版本化开发资料的主要来源。
- Google Drive 可作为团队文档协作位置。
- 不要创建重复的 `skills/`、`templates/` 项目目录。
- Skill 本身不属于产品项目目录。

如果相关 connector 尚未连接，先按当前会话可用的文件能力工作，不要假装已经写入外部系统。

## 3. 工作流

1. 创建或复用 `<ProductName>/01-产品定义/`。
2. 初始化或复用上述 6 个 Markdown 文件。
3. 将用户原始想法和迭代记录写入 `01-基本描述.md`。
4. 按顺序填充 01 → 02 → 03 → 04 → 05 → 06。
5. 每一轮只聚焦当前文件或一个明确的问题类别。
6. 信息缺失时，将精确问题写入 `05-开放问题.md`，不要擅自编造决策。
7. 先只询问阻塞问题。聊天回复必须完整列出每个阻塞问题的 ID、需要确认的决策、为什么重要、推荐方案/选项。
8. 用户回答后，先更新受影响文件及 `05-开放问题.md`，并将问题转为 `Resolved` 或 `Deferred by user`。
9. 阻塞问题解决后，再在单独一轮询问非阻塞问题；同样必须在聊天中完整列出。
10. 只有 `05-开放问题.md` 中没有任何 `Open` 问题，并且用户确认产品方向后，才能冻结。
11. 将最终产品定型稿写入 `06-最终定型稿.md`。
12. 如果用户要求完整 PRD，不要把定型稿扩写成长 PRD；切换到 PRD Make，并将冻结版定型稿作为主要事实来源。

## 4. 六个文件的用途

### 01-基本描述.md
记录原始需求、一句话定位、目标用户、业务目标、已知约束和迭代记录。

### 02-JTBD场景.md
记录 JTBD、Job Stories、ES 风格触发条件场景和场景优先级。

### 03-范围边界.md
记录产品形态、MVP 范围、暂缓范围、技术偏好、已确认假设和明确不做。

### 04-页面流程.md
记录页面清单、主流程、分支流程、状态流转、核心数据对象和权限。

### 05-开放问题.md
集中记录阻塞问题、非阻塞问题、延后决策、已确认决策、风险备注以及冻结规则。

### 06-最终定型稿.md
保存冻结版 Product Shipping Brief、冻结检查和变更记录。

## 5. 提问规则

只询问会改变以下内容的问题：
- 产品行为
- 工程范围
- 数据模型
- 权限
- 核心流程
- 交付优先级
- MVP 边界
- 关键业务规则

优先提出成组的具体问题，不做泛泛头脑风暴。

### 对话规则

- 不允许要求用户打开工作区文件才能回答问题；当前问题必须完整出现在聊天中。
- 分两轮提问：先阻塞问题，再非阻塞问题。除非用户明确要求完整列表，否则不要混在同一轮。
- 每个问题必须包含：问题 ID、需要确认的决策、为什么重要的一句话说明、推荐方案或选项。
- 问题较多时，一轮只聚焦一个类别。
- 用户回答一轮后，先更新 `05-开放问题.md`、已确认决策、延后决策和受影响产品文件，再进入下一轮。
- 建议不是决策。只有用户明确确认后，才能成为已确认决策。
- 不允许把 Skill、模型或“PM Make 默认假设”作为决策来源。

## 6. 必问维度

根据实际产品情况覆盖：

- 产品一句话：为谁、在什么场景、解决什么高价值问题。
- 目标用户：主用户、决策者、影响者、被影响者。
- JTBD：情境、动机、期望进展、功能/情感/社会任务。
- 当前替代方案：用户现在如何解决、痛点、切换阻力。
- MVP 边界：必须有、暂缓、不做。
- 核心流程：入口、主路径、关键分支、失败/空/等待状态。
- 页面与信息架构：页面清单、页面职责、跳转关系。
- 业务规则：状态、权限、数据来源、关键约束。
- 技术边界：平台、主要交互、AI 参与方式、系统集成、数据存储、登录/鉴权。

不要求每个产品机械回答所有问题；只询问对当前产品真正有影响的内容。

## 7. 状态规则

- `Open`：产品仍在澄清中。
- `Resolved`：用户已明确确认。
- `Deferred by user`：用户明确接受 MVP 推荐默认值，或明确把主题推迟到后续 PRD/技术设计阶段。
- 冻结前任何问题都必须变成 `Resolved` 或 `Deferred by user`。
- 只要存在任何 `Open`，包括非阻塞问题，就不能冻结。
- 延后决策必须有用户或用户提供文档作为来源。

## 8. 定型通过标准

只有同时满足以下条件，才建议进入 PRD 或原型：

- 产品定位能用 1–2 句话准确表述。
- 至少 1 个核心用户、1 个核心场景、1 条主流程明确。
- MVP 有明确“做 / 不做 / 待确认”边界。
- 关键业务规则、权限、数据对象没有被含糊带过。
- 未确认内容已集中写入 `05-开放问题.md`。
- 所有开放问题均已解决或由用户明确延后。
- 用户明确确认产品方向。

## 10. 最终定型稿格式

冻结稿必须使用：

```markdown
# 产品定型稿（Product Shipping Brief）

## 1. 一句话定位

## 2. 目标用户

## 3. 核心场景

## 4. 产品形态

## 5. MVP 范围

## 6. 页面与主流程

## 7. 数据与权限

## 8. 暂缓范围
```

不要把定型稿扩写成长 PRD。

## 11. 文件操作原则

- 优先编辑现有文件，而不是重复创建。
- 保持文件名完全一致。
- 不随意改变模板标题、字段和顺序。
- 不删除用户已经确认的内容。
- 用户修改决策后，同步更新受影响文件。
- 变更必须可从迭代记录或已确认决策追溯。
- 如果无法访问外部 GitHub/Google Drive，不得声称已写入；应明确说明当前可用范围。

## 12. 业务终点与停止条件（2026-11-05 复盘补充）

- 在定型前明确用户要达到的**业务结果**、验收人、可观察的成功标准和本次工作终点：需求定型、代码更新、GitHub 合并、现有产品功能验收，或实际发布。技术流水线是实现手段，不自动成为业务目标。
- 对既有产品，先确认当前功能是否已满足需求；用户确认已满足且没有要求强制发布时，不把部署列为必经阶段。
- 将「功能已获用户确认」「代码已合并」「已部署」「来源已核实」分别记录，不互相推导；记录尚未验证的事项。
- 用户变更目标时，及时调整范围和停止条件；不把已取消工作重新列为待办。不得以定型稿代替测试或发布证据。
